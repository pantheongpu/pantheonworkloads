# Real GPU against its simulated counterpart

Generated by `tools/sim_vs_gpu.py` (`bin/pw coverage --write`) from the files in `docs/data/sim-vs-gpu/`; do not edit by hand. Every value below is a row of those files, and each row names its source (a document and section, or a workflow run, artifact and commit). `bin/pw coverage --check` fails in CI when this page and the data differ.

## How to read this

- **pantheonsim has no timing model.** It is a functional simulator: it says whether a simulated GPU gives the same answers as a real one, never how fast the real one is. Its wall-clock is CPU time on whatever host ran it. Table 2 shows that time as the cost of simulating, not as GPU performance, and no simulated number is placed beside a real throughput. `bin/pw` still refuses benchmark metrics on `sim:` targets; this page does not change that.
- **Parity** means: the same workload, checked against the same reference with the same tolerance, gives the same verdict on the real card and on the simulated one, and the deviations from the reference are of the same size. It does not mean the simulated card is as fast, and PASS on both sides only says both stayed inside the tolerance.
- **Pairing.** The real NVIDIA A10G (AWS g5, sm_86) is paired with `sim:nvidia/a10g`, and the real NVIDIA L40S (AWS g6e, sm_89) with `sim:nvidia/l40s`; both profiles were characterized on those parts (pantheonsim `nvidia/docs/profiles.md`). The L40S has real results only for the stage-2a catalog workloads (llama.cpp and diffusion), while the simulated workloads are the PyTorch arch-*, lib-* and training ones, so the L40S pair has no workload in common (see *No counterpart*). The other simulated profiles are shown as PASS / FAIL / SKIP columns for the same A10G workload (`a10` is the generic A10, a different profile from `a10g`); "not run" means no result exists, not a pass.
- **Same reference and tolerance** is checked from the repository, not assumed: the real run and the simulated run used workload directories that are identical (manifest, `reference.json` and scripts) between the two commits named in the data, except where the row says otherwise. Where the real rerun and a scheduled nightly run on main used the same commit, that is the basis (the same commit, so the same files). The simulated a10g / l40s results are the scheduled nightly run on main named in the data sets below.
- **Never estimated.** An empty cell is a value the sources do not hold. Real wall-clock seconds exist only for the workloads of the real rerun (14 workloads, 42 runs, each one a row of `real_runs.tsv`); a workload outside it has an empty real cell and no ratio.
- **Software.** The real rerun and the nightly simulation used the same libraries: torch 2.14.1+cu130, torchvision 0.29.1 and transformers 5.18.0 (the version the references were recorded with; the older real records of 2026-10-08 used 5.19.0 for the arch-* workloads and are marked superseded where the rerun replaces them).

## Table 2: cost of simulation

Columns headed *cost of simulating (CPU time), not GPU performance* are the wall-clock seconds of one `bin/pw run` on the simulator (starting it, importing torch, running the workload on the host CPU). They say nothing about how long the real card takes. The nightly times come from a GitHub-hosted runner whose load the artifact does not record. Real A10G seconds are the whole-workload wall-clock `bin/pw run` writes to `results.tsv` (process start, imports and the workload's own CPU float64 oracle included, the same quantity as the simulated column), measured on one idle A10G; *median* is the median of three consecutive runs, *first run* is the cold one (empty file and kernel caches after setup). sim/real is the simulated seconds divided by the real median: how many times slower it is to simulate the workload than to run it on the card, not a statement about GPU speed.

## What the real-side rerun filled, and what is still missing

The rerun proposed in the first version of this page has been done (2026-10-22: g5.2xlarge, NVIDIA A10G, driver 595.91.07, CUDA 13.0, Ubuntu 22.04 DLAMI, torch 2.14.1+cu130, torchvision 0.29.1+cu130, transformers 5.18.0, numpy 2.5.4 (venv, uv Python 3.12); three consecutive `bin/pw run <w> --target gpu` per workload, nothing else on the GPU). It ran the 14 workloads of Table 1 that the PyTorch rig can run, from workloads 659c10a (same commit as run 39585402659), which is the commit of the scheduled nightly run the simulated side is taken from. It supplied:

1. **Real wall-clock seconds** for 14 of 14 workloads, three runs each (`real_runs.tsv`); Table 2 now has the sim/real ratio for every workload the nightly runs on `sim:nvidia/a10g`.
2. **Per-workload deviation figures** for the eight that had none or one shared figure (the five arch-* workloads, gpt-train-fp32, gpt-train-bf16, resnet18-randinit-pytorch); figures still missing in Table 1: none.
3. **The same commit on both sides**, so the same reference and tolerance is a fact of the commit, not of a diff.

Still missing: a second real card (no L40S real run of these workloads exists, so `l40s` stays unpaired); a scheduled main run of the nightly for the rows that come from a pull-request run (see the data sets); more than one rig and day (the run-to-run spread seen here is three consecutive runs on one idle card); and the *no counterpart* workloads, whose reasons are in the section above: for `sim-not-run` the missing side is the simulated one (a hosted run for the workloads that need a model download), and the L40S workloads have no sim target in their manifests, so giving them one is a workload change.
