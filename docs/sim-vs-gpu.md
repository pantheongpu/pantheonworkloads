# Real GPU against its simulated counterpart

Generated by `tools/sim_vs_gpu.py` (`bin/pw coverage --write`) from the files in `docs/data/sim-vs-gpu/`; do not edit by hand. Every value below is a row of those files, and each row names its source (a document and section, or a workflow run, artifact and commit). `bin/pw coverage --check` fails in CI when this page and the data differ.

## How to read this

- **pantheonsim has no timing model.** It is a functional simulator: it says whether a simulated GPU gives the same answers as a real one, never how fast the real one is. Its wall-clock is CPU time on whatever host ran it. Table 2 shows that time as the cost of simulating, not as GPU performance, and no simulated number is placed beside a real throughput. `bin/pw` still refuses benchmark metrics on `sim:` targets; this page does not change that.
- **Parity** means: the same workload, checked against the same reference with the same tolerance, gives the same verdict on the real card and on the simulated one, and the deviations from the reference are of the same size. It does not mean the simulated card is as fast, and PASS on both sides only says both stayed inside the tolerance.
- **Pairing.** The real card is the NVIDIA A10G (sm_86), paired with `sim:nvidia/a10`. The L40S has no simulated profile, so its workloads can only appear under *no counterpart*. The other simulated profiles are shown as PASS / FAIL / SKIP columns for the same workload; `-` / "not run" means no result exists, not a pass. `rtx3060` and `rtx3080ti` share the A10G's architecture (sm_86) and are the nearest cards with data when `a10` was not run.
- **Same reference and tolerance** is checked from the repository, not assumed: the real run and the simulated run used workload directories that are identical (manifest, `reference.json` and scripts) between the two commits named in the data.
- **Never estimated.** An empty cell is a value the sources do not hold. In particular no per-workload wall-clock of a real run is recorded anywhere, so the real column of Table 2 and the sim/real ratio are empty.
- **Software differs a little.** The real re-run used transformers 5.19.0, the nightly simulation 5.18.0 (the version the references were recorded with); both used torch 2.14.1+cu130.

## What is missing on the real side, and what a single-A10G rerun would add

None of this has been launched; it is a proposal for the maintainer to approve. The 14 workloads of Table 1 would be re-run once on one on-demand A10G (g5.xlarge or g5.2xlarge, `tools/rig`, about 45 minutes of instance time at the rate the torch 2.14.1 re-run took), from the same commit as a nightly simulated run, with `bin/pw run <workloads> --target gpu` and the torch 2.14.1 environment of `docs/first-gpu-run-a10g.md`:

1. **Real wall-clock seconds** for all 14 workloads (`results.tsv` of `bin/pw run` records them). Missing today for 14 of 14; without them Table 2 has no ratio.
2. **Per-workload deviation figures** where the docs give none or one shared figure: arch-encdec, arch-llama-family, arch-moe, arch-ssm, arch-vision, gpt-train-fp32, gpt-train-bf16, resnet18-randinit-pytorch.
3. **The same commit on both sides**: the real run used 479c1c7 and the nightly 5c2f647 (identical workload directories, but a rerun makes that a fact of one run rather than of a diff).
4. A real record to put next to the *whole-workload* `sim:nvidia/a10` runs, which do not exist yet. The rig cannot produce them: add `a10` to the nightly workflow's matrix (a CPU-only hosted job, no rig) and the pairing columns fill in 14 workloads at once, including the seconds Table 2 needs on the simulated side.

A rig adds nothing for the *no counterpart* workloads whose reason is `sim-not-run` or `no-sim-profile`: their missing side is the simulated one (a hosted run for the workloads that need a model download, or a new profile for the L40S).
